# Nexus Defense — API набора элементов ландшафта

> Последнее обновление: 2026-09-29
> Кому: компоновщику карты (основной компонент) и агентам

Этот документ — контракт между **набором деталей** и **компоновщиком карты**.
Набор ничего не знает о карте: ни про шум, ни про дорогу, ни про сетку. Компоновщик
ничего не знает о конкретных деталях: ни про их геометрию, ни про материалы.
Единственная связь между ними — перечисленные ниже функции.

Справочник по всем 22 деталям с параметрами: [`kit-reference.md`](kit-reference.md)
(генерируется из кода, руками не правится).

---

## 1. Импорт

Всё, что нужно компоновщику, берётся из одного входа:

```js
import {
  ELEMENTS, BY_ID, GROUPS, elementsOf,   // реестр
  KIND, LIQUID, PROFILES,                // перечисления
  stampElement,                          // впечатать деталь в карту
  elementMesh, disposeElement,           // меш детали и его освобождение
  BIOME, BIOME_INFO                      // палитра биомов
} from './src/terrain/elements/index.js';
```

## 2. Два объекта: шаблон и экземпляр

| | Что это | Изменяемый? |
|---|---------|-------------|
| **Шаблон** | описание детали из реестра (`ELEMENTS`, `BY_ID.get(id)`) | нет, общий на всю карту |
| **Экземпляр** | `el.instantiate({ ...params })` — шаблон со своими параметрами | нет, параметры заморожены |

```js
const lake = BY_ID.get('lake');                 // шаблон
const a = lake.instantiate({ anchorY: 12 });    // экземпляр для одной котловины
const b = lake.instantiate({ anchorY: -4 });    // второй, не мешает первому
a.params.anchorY !== b.params.anchorY;         // true
```

Шаблон безопасно ставить на карту сколько угодно раз: изменяемого состояния на нём нет.
Один шаблон — один меш на все экземпляры, поэтому **меш экземпляра кэшируется**
(`elementMesh(inst)`), а повторный вызов просто отдаёт тот же объект.

## 3. Поля шаблона

| Поле | Тип | Смысл |
|------|-----|--------|
| `id` | string | стабильный ключ, для правил компоновщика и сохранений |
| `name` | string | имя для интерфейса |
| `kind` | `KIND.RELIEF\|WATER\|BIOME\|LINK` | категория |
| `profile` | `peak\|bowl\|flat\|liquid\|step` | форма профиля, см. §5 |
| `radius` | number | внешний радиус: след с юбкой |
| `core` | number | радиус жёсткого ядра |
| `cost` | number | вес для баланса карты |
| `tags` | string[] | `water`, `cliff`, `wall`, `long`, `hazard`, `fire`, `biome`… |
| `note` | string | описание для игрока |
| `defaults` | object | параметры по умолчанию |
| `shape(dx, dz)` | fn | расстояние до центра; по умолчанию круг |

## 4. Методы

```js
el.instantiate(params)      // -> экземпляр с params = {...defaults, ...params}
el.heightAt(x, z, base, ox, oz, p)   // ДЕЛЬТА высоты
el.biomeAt(x, z, p)        // id биома или -1
el.liquid({ p, at })       // { kind, level, feather } | null
el.canPlaceAt(ctx)         // { ok: bool, why?: string }
el.props(rng, p)           // [[x, z, scale, rot, dy?], ...]
elementMesh(inst)          // THREE.Object3D, кэшируется
disposeElement(inst)       // освободить геометрии и материалы меша
stampElement(inst, h, B, g, at)  // впечатать в карту
```

### Ключевое: `heightAt` возвращает дельту

```js
// base — ТЕКУЩАЯ высота в этой точке, не ноль
el.heightAt(x, z, base, ox, oz, p) -> number   // что прибавить к base
```

Компоновщик делает ровно это:

```js
h[idx] = h[idx] + el.heightAt(x, z, h[idx], at.x, at.z, inst.params);
```

`base` нужен деталям, которые **выравнивают** поверхность: озеро не должно лежать
вровень с наклонным склоном, оно должно вырезать горизонтальную чашу. Поэтому
у озера в параметрах есть `anchorY` — отметка, на которую компоновщик поставил деталь.

Порядок аргументов легко перепутать (`p` стоит шестым). Ошибка не бросается —
молча даёт `NaN` в геометрии. Если в превью меш пустой или чёрный, проверь эту
сигнатуру первой.

## 5. Профили

| Профиль | Что делает с рельефом | Элементы |
|---------|----------------------|----------|
| `peak` | вершина в центре, к краю сходит в ноль | холм, гряда, плато, скалы, дюна, вулкан |
| `bowl` | чаша, минимум в центре | котловина |
| `flat` | почти не гнёт рельеф, только пятно | лес, степь, коса, снег, кристаллы, каменное поле, насыпь |
| `liquid` | выравнивает дно к своему уровню | озеро, яд, расплав, ручей |
| `step` | разрыв или ступень | уступ, мост, порог |

## 6. `stampElement` — единственная точка записи в карту

```js
const res = stampElement(inst, h, B, g, { x, z });
// g = { RES, STEP, WORLD, idx: (i, j) => j * RES + i }
// res = { minH, maxH, cells, liquid }
```

Компоновщик держит **два плоских массива**:

```js
const h = new Float32Array(RES * RES);   // высоты
const B = new Uint8Array(RES * RES);     // биомы
```

`stampElement` сам обходит след детали и пишет в них. Компоновщику не нужно знать,
как устроен профиль, — достаточно вызвать функцию и посмотреть на `res`.

## 7. Жидкости

Деталь с `liquid()` возвращает `{ kind, level }`. Уровень — **абсолютная отметка**,
её компоновщик кладёт на общий уровень озера при сборке сцены.

```js
const { kind, level } = inst.liquid({ p: inst.params, at });
```

Готовая реализация отрисовки — `src/terrain/liquids.js`. Ей нужны две текстуры
по сетке карты:

| Текстура | Формат | Содержимое |
|----------|--------|------------|
| высота | `RedFormat` + `FloatType`, `LinearFilter` | `H` по сетке |
| владение | `RedFormat` + `UnsignedByteType`, `LinearFilter` | 0 — нет, 1 — вода, 2 — яд, 3 — лава |

**Важно:** строки обеих текстур пишутся в обратном порядке по Z. `PlaneGeometry`
после `rotateX(-π/2)` отображает локальный `y` в мировой `−z`, поэтому `v=0`
у геометрии соответствует `z = +WORLD/2`, а первая строка данных — `z = -WORLD/2`.
Без разворота шейдеры семплят высоту зеркально и не находят ничего.
Готовые сборщики текстур: `buildHeightTexture`, `buildOwnershipTexture`
в `src/terrain/world.js`.

## 8. `canPlaceAt` — правила постановки

```js
const ctx = { h, slope, distRoad, near, overLiquid };
const { ok, why } = el.canPlaceAt(ctx);
```

| Поле `ctx` | Тип | Значение |
|------------|-----|----------|
| `h` | number | текущая высота в точке |
| `slope` | number | уклон (0…1) |
| `distRoad` | number | расстояние до полотна дороги, 0 — нет дороги рядом |
| `near` | array | id соседних деталей |
| `overLiquid` | boolean | под точкой есть жидкость |

Правила — **рекомендация компоновщику**, а не запрет. Набор их не навязывает:
`stampElement` поставит деталь куда угодно. Правила нужны, чтобы карта
не получалась бессмысленной (уступ на вершине, озеро на отвесе).

## 9. Как компоновщику решать конфликты

Детали складываются **суммированием дельт**, поэтому:

- **порядок не важен** — результат одинаков при любом;
- **перекрытие складывается** — два холма в одной точке дают сумму высот;
- **юбка гасит края**, поэтому соседние детали срастаются без шва;
- **жидкости не суммируются** — уровень задаётся явно, последний поставленный
  с тем же `kind` переопределяет уровень в `levels`.

Детали с `tags.includes('biome')` красят биом; детали с `liquid` помечают
свою территорию как жидкость. Порядок отрисовки: сначала рельеф, потом биомы,
потом вода по маске владения.

## 11. Чего набор не делает

- **не строит карту** — это дело компоновщика;
- **не знает про дорогу** — в наборе только насыпь и мост как перемычки;
- **не решает баланс** — `cost` и `tags` даны, решение за компоновщиком;
- **не генерирует рельеф из шума** — только параметризованные детали.

## 12. Компоновщик карты

Компоновщик — слой между набором и картой. Он больше не «демонстрируется
в песочнице», а написан: `src/composer/`.

```js
import { composeMap, roadAt, contextAt } from './src/composer/composer.js';
import { OWNER_NETWORK, OWNER_PLATE, OWNER_BASE } from './src/composer/network.js';

const map = composeMap({ plate: OWNER_PLATE, network: OWNER_NETWORK, base: OWNER_BASE });
```

### Описание карты

| Поле | Смысл |
|------|-------|
| `plate` | `{ size, res, baseY, biome }` — плита и её сетка |
| `network` | `{ halfWidth, segments }` — сеть дороги, обязательна |
| `base` | `{ x, z, half }` или `null` |
| `details` | `[{ element, at: {x,z}, params, force }]` — детали набора |
| `road` | `{ skirt, lift }` — откос и подъём полотна |

Порядок сборки зафиксирован и **важен**: базовый рельеф → детали набора →
дорога. Дорога кладётся последней, потому что выравнивает рельеф под
полотном; если её положить раньше, насыпь и мост окажутся пересыпанными.
Поле расстояний до дороги считается **до** постановки деталей: `canPlaceAt`
ждёт `distRoad` независимо от того, что уже лежит на карте.

### Что отдаёт компоновщик

| Поле | Смысл |
|------|-------|
| `grid`, `h`, `B` | сетка и две таблицы |
| `road.dist` | расстояние до объединения полотен, 0 внутри |
| `road.entries` | входы — отрезки, конец которых на краю плиты |
| `road.probes` | середина каждого отрезка: критерий «сеть на месте» |
| `road.target` | отметка полотна (средняя по дороге плюс подъём) |
| `details` | принятые детали с инстансами и результатом `stampElement` |
| `rejected` | отклонённые правилами постановки, с причиной |
| `endProblems` | нарушения правила концов (пусто — сеть корректна) |

Проверка без браузера: `node --import ./tools/register-stub.mjs tools/check-network.mjs`.

### Дорога

Дорога принадлежит компоновщику (решение от 2026-09-29). Сеть — это
отрезки осевых линий, полотно — **объединение** прямоугольников, которые
из них получаются. Объединение, а не «сложить прямоугольники»: при
полуширине 2.4 внутренняя и внешняя стороны угла поворота разной длины,
и наивная сборка в 3D даёт нахлёст — два меша в одной точке. Здесь
поверхность одна, а край задаётся расстоянием до объединения, поэтому
стык корректен по построению.

**Правило концов.** Каждый конец отрезка упирается в край того, к чему
примыкает: край полотна (крайнее ±`halfWidth` от линии), край базы или
край плиты. `checkEnds` проверяет сорок концов. Правило, а не двадцать
пар чисел: попиксельное чтение рисунка оставляет в данных шум до 0.12
единицы, и конец, не попавший в край, рассыпает стык именно там.
